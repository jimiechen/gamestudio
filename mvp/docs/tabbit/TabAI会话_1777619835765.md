# **数值平衡 TDD 化 + 你这个"子弹变少"Bug 的精确定位**

你提的两个问题分别戳中了游戏开发的两个深层痛点：**数值平衡需不需要测试覆盖？** 和 **看似工作正常的功能其实是 Bug？** 答案都是肯定的。下面分两部分讲清楚——先解决眼前 Bug，再给出数值推演的 TDD 方法论。

## **一、"伤害 +1 子弹反而变少" —— 这是真 Bug，而且测试能抓到**

### **1.1 你的直觉是对的：词条设计有问题**

先把概念理顺：

- **"伤害 +1"** 在 PRD 里的定义是**单发子弹的伤害值 +1**，不是"多发射一颗子弹"
- **"屏幕上同时存在 2 颗子弹"** 是因为攻击间隔 0.6s + 子弹存活 1.5s，理论上稳态下屏幕上有 `1.5 / 0.6 ≈ 2.5` 颗子弹

所以你看到的现象——**初始有 2 颗子弹，升级后变 1 颗** —— 不是"伤害 +1 让子弹变少"，而是**两个独立 Bug 叠加**导致的视觉错觉。

### **1.2 真正的 Bug 在哪里**

打开 `Player.gd`，看 `_on_attack_timer` 函数：

```gdscript
func _on_attack_timer() -> void:
    _refresh_attack_rate()   # ← 问题在这一行
    var target := _find_nearest_enemy()
    ...
```

**Bug A：`_refresh_attack_rate()` 在每次发射后才刷新**，意味着第一次升级"攻速 +10%"后，要等当前这颗子弹打完才生效，玩家会觉得"升级好像没反应"。

**Bug B（关键）**：看 `_refresh_attack_rate`：

```gdscript
func _refresh_attack_rate() -> void:
    attack_timer.wait_time = max(0.08, base_attack_interval / GameManager.attack_rate_mult)
```

**Godot 的 Timer 在运行中改 `wait_time`，不会立刻应用，要等当前周期结束**。但更糟糕的是，如果你看 `_ready` 里：

```gdscript
attack_timer.wait_time = 0.6        # autostart 默认值
attack_timer.start()                 # 启动
_refresh_attack_rate()              # 又改 wait_time
```

启动顺序导致**第一颗子弹会在很短时间内被发出，造成"开局看起来有 2 颗"的假象**，而后续稳定下来后实际只有 1~2 颗循环。

**Bug C（你的真痛点）**：升级"伤害 +1"完全不影响发射数量，但屏幕子弹数量看起来变少，原因是——升级面板暂停游戏期间，**已经在飞的子弹因 LifeTimer 继续走**（如果 LifeTimer 没设 `process_mode`），暂停结束时屏幕上一颗子弹都没了，给你"变少"的错觉。

### **1.3 你真正想要的是"伤害 +1" → "弹幕 +1"**

如果你的设计意图是**升级让弹幕越来越密**（这才是肉鸽爽点），PRD 里的词条池应该重新设计。我建议改成下面这套：

| 词条 ID | 显示文本 | 实际效果 | 数值变化 |
|---|---|---|---|
| `damage` | 伤害 +1 | 每颗子弹 damage +1 | 加法 |
| `multishot` | 弹幕 +1 | 每次发射多 1 颗子弹（散射） | 加法上限 5 |
| `attack_speed` | 攻速 +15% | 攻击间隔缩短 | 乘法 |
| `move_speed` | 移速 +10% | 玩家移速 | 乘法 |
| `pierce` | 穿透 +1 | 子弹命中后不消失，可穿 N 次 | 加法上限 3 |
| `bullet_speed` | 弹速 +20% | 子弹速度 | 乘法 |

**这才是真正的肉鸽体验**——前 5 级感觉每次升级都让弹幕密度肉眼可见地增长。

### **1.4 用测试把这个 Bug 钉死**

在 `tests/integration/` 加一条测试，**它会立刻让你之前的"伤害+1"实现暴露问题**：

```gdscript
# tests/integration/test_upgrade_visual_feedback.gd
extends GutTest

func test_multishot_upgrade_increases_bullet_count() -> void:
    var main := load("res://scenes/Main.tscn").instantiate()
    add_child_autofree(main)
    await get_tree().process_frame
    
    var player := get_tree().get_nodes_in_group(&"player")[0]
    
    # 放一个敌人让玩家有目标
    var enemy_scene: PackedScene = load("res://scenes/Enemy.tscn")
    var enemy := enemy_scene.instantiate()
    enemy.global_position = player.global_position + Vector2(200, 0)
    main.add_child(enemy)
    
    # 触发一次发射，记录子弹数
    player._on_attack_timer()
    await get_tree().process_frame
    var bullets_before: int = _count_bullets()
    
    # 应用 multishot 升级
    GameManager.apply_upgrade("multishot")
    player._on_attack_timer()
    await get_tree().process_frame
    var bullets_after: int = _count_bullets()
    
    assert_eq(bullets_after - bullets_before, 1, 
        "multishot upgrade should add exactly 1 more bullet per fire")

func _count_bullets() -> int:
    return get_tree().get_nodes_in_group(&"bullet").size()


func test_damage_upgrade_does_not_change_bullet_count() -> void:
    # 反向测试：伤害词条不应改变子弹数量
    var main := load("res://scenes/Main.tscn").instantiate()
    add_child_autofree(main)
    await get_tree().process_frame
    var player := get_tree().get_nodes_in_group(&"player")[0]
    
    var enemy_scene: PackedScene = load("res://scenes/Enemy.tscn")
    var enemy := enemy_scene.instantiate()
    enemy.global_position = player.global_position + Vector2(200, 0)
    main.add_child(enemy)
    
    player._on_attack_timer()
    await get_tree().process_frame
    var before: int = _count_bullets()
    
    GameManager.apply_upgrade("damage")
    player._on_attack_timer()
    await get_tree().process_frame
    var after: int = _count_bullets()
    
    assert_eq(after - before, 0, "damage upgrade must NOT change bullet count")
```

这两条测试一起跑，能精确告诉你：词条作用是否符合 PRD 描述。

## **二、数值平衡的 TDD 化 —— 用极限推演代替"我感觉"**

游戏开发里最容易被忽视的一类 Bug 是**数值失衡**：不崩不报错，但玩家体验崩了（例如 5 分钟无敌、30 秒就死、永远无法升 10 级）。**这恰恰是测试覆盖率最该去的地方**。

### **2.1 三类必须测试的极限值**

| 类型 | 含义 | 举例 | 必须测什么 |
|---|---|---|---|
| **边界值（Boundary）** | 数值的物理/逻辑下限上限 | 攻速 `wait_time` 不能 ≤ 0 | 夹紧函数 |
| **临界值（Threshold）** | 玩法体验的拐点 | 升 10 级需要的总经验、击杀数 | 累计公式 |
| **稳态值（Steady State）** | 长时间运行后的均衡数值 | 60 秒后屏幕敌人数、DPS 曲线 | 仿真测试 |

### **2.2 边界值测试（U21~U25 新增到单元测试）**

```gdscript
# tests/unit/test_extreme_values.gd
extends GutTest

func test_attack_rate_clamped_to_min_when_mult_huge() -> void:
    # 攻速倍率叠到天上，wait_time 不能为 0 或负数
    GameManager.attack_rate_mult = 10000.0
    var wait: float = max(0.08, 0.6 / GameManager.attack_rate_mult)
    assert_gte(wait, 0.08, "attack timer must not go below safety floor")

func test_xp_threshold_grows_monotonically() -> void:
    # 升级阈值必须单调递增，否则会出现 bug：升级反而更容易
    var prev: int = 5
    for i in 30:
        var next: int = MathUtils.calc_next_threshold(prev)
        assert_gt(next, prev, "threshold at level %d must grow" % i)
        prev = next

func test_xp_threshold_reasonable_at_level_30() -> void:
    # 极限推演：30 级时单级所需经验应在合理区间，否则后期玩不下去
    var threshold: int = 5
    for i in 29:
        threshold = MathUtils.calc_next_threshold(threshold)
    # 30 级应在 1000~5000 之间（设计意图：单局 5~10 分钟到 30 级）
    assert_between(threshold, 1000, 5000, "level 30 threshold sanity")

func test_enemy_health_growth_bounded() -> void:
    # 敌人血量随时间增长，10 分钟（600 秒）后不能高到无法击杀
    var hp_at_10min: int = 3 + int(600 / 15.0)  # = 43
    var player_dps: float = 1.0 / 0.6  # 1 伤害 / 0.6 秒
    var ttk: float = float(hp_at_10min) / player_dps
    assert_lt(ttk, 30.0, "10min enemy must be killable within 30s by base player")

func test_player_with_max_upgrades_still_balanced() -> void:
    # 极限：连升 20 级全部攻速，wait_time 不会变成 NaN/0
    for i in 20:
        GameManager.apply_upgrade("attack_speed")
    var wait: float = max(0.08, 0.6 / GameManager.attack_rate_mult)
    assert_gt(wait, 0.0, "no division by zero or negative")
    assert_lte(GameManager.attack_rate_mult, 100.0, "attack rate mult sanity cap")
```

### **2.3 稳态仿真测试（最强大的一类）**

这种测试**让游戏在无人操作下跑 60 秒，断言数值在合理区间**。它能发现纯逻辑测试根本看不到的设计问题。

```gdscript
# tests/e2e/test_balance_simulation.gd
extends GutTest

func test_player_survives_first_minute_with_no_upgrades() -> void:
    # 平衡推演：完全不升级、不移动，玩家应在 30~90 秒内死亡
    # 太短 = 太难，太长 = 太简单
    var main := load("res://scenes/Main.tscn").instantiate()
    add_child_autofree(main)
    await get_tree().process_frame
    
    # 自动拒绝所有升级（mock）
    GameManager.level_up.connect(func(_lv): pass)  # 不弹面板
    
    var player := get_tree().get_nodes_in_group(&"player")[0]
    var death_time: float = -1.0
    var elapsed: float = 0.0
    while elapsed < 120.0 and is_instance_valid(player):
        await get_tree().physics_frame
        elapsed += get_physics_process_delta_time()
    death_time = elapsed
    
    assert_between(death_time, 30.0, 90.0, 
        "no-upgrade no-move death time should be 30~90s, got %.1f" % death_time)


func test_xp_per_minute_in_steady_state() -> void:
    # 60 秒内玩家应能达到 5~12 级（单局节奏）
    var main := load("res://scenes/Main.tscn").instantiate()
    add_child_autofree(main)
    await get_tree().process_frame

    var spawned: int = 0
    var stub_timer := Timer.new()
    stub_timer.wait_time = 0.1
    stub_timer.autostart = true
    stub_timer.timeout.connect(func():
        for e in get_tree().get_nodes_in_group(&"enemy"):
            if is_instance_valid(e):
                e.take_damage(999)

    )
    main.add_child(stub_timer)
    
    await wait_seconds(60.0)
    
    assert_between(GameManager.level, 5, 12,
        "1min level should be 5~12, got %d (killed %d enemies)" % [GameManager.level, spawned])


func test_screen_enemy_count_does_not_explode() -> void:
    # 极限：玩家完全不输出，敌人数量是否会炸内存
    var main := load("res://scenes/Main.tscn").instantiate()
    add_child_autofree(main)
    await get_tree().process_frame
    
    var player := get_tree().get_nodes_in_group(&"player")[0]
```

### **2.4 抽卡变化不大的本质 + 测试方法**

你说"抽卡变化不大"，这是因为**当前词条池只有 3 条且效果数值很温和**。要让升级有"爽感"，需要：

1. **扩大词条池到 6~8 条**（如 1.3 节我列的 6 条）
2. **首次出现的词条给更大数值**（首拿伤害 +2，叠加后才 +1）
3. **加入"质变"类词条**（穿透、弹幕数）

测试这个的方法：**变异度测试（Mutation Test）**——验证不同升级路线产生显著不同的体验。

```gdscript
# tests/e2e/test_upgrade_diversity.gd
func test_different_upgrade_paths_produce_different_dps() -> void:
    # 路线 A：纯伤害
    var dps_a: float = _simulate_path(["damage", "damage", "damage", "damage", "damage"])
    # 路线 B：纯攻速
    var dps_b: float = _simulate_path(["attack_speed", "attack_speed", "attack_speed", "attack_speed", "attack_speed"])
    # 路线 C：混合
    var dps_c: float = _simulate_path(["multishot", "damage", "pierce", "attack_speed", "multishot"])
    
    # 三条路线 DPS 必须有显著差异（>20%），否则升级没意义
    var max_dps: float = max(dps_a, max(dps_b, dps_c))
    var min_dps: float = min(dps_a, min(dps_b, dps_c))
    var diversity: float = (max_dps - min_dps) / max_dps
    
    assert_gt(diversity, 0.2, 
        "upgrade paths too similar: A=%.1f B=%.1f C=%.1f diversity=%.2f" 
        % [dps_a, dps_b, dps_c, diversity])

func _simulate_path(path: Array[String]) -> float:
    GameManager.start_run()
    for upgrade_id in path:
        GameManager.apply_upgrade(upgrade_id)
    # 计算理论 DPS
    var damage: float = 1.0 + GameManager.bonus_damage
    var fire_rate: float = GameManager.attack_rate_mult / 0.6
    var multishot: int = 1 + GameManager.get("bullet_count_bonus")  # 需要新加字段
    return damage * fire_rate * multishot
```

**这条测试一旦失败，就证明你的词条池设计同质化严重，玩家无论怎么选都没区别**——这是肉鸽的致命伤，普通测试根本发现不了。

## **五、回答你最初那个哲学问题**

**"游戏开发是不是要测试推演出极限值？"** —— 这不仅是"应该"，而是**专业游戏开发与业余游戏开发的分水岭**。

业余开发者靠"我玩了一把感觉差不多"，专业开发者靠**数值仿真测试 + 极限边界断言**。Supercell、Riot、米哈游内部都有专门的"平衡测试机器人"，跑成千上万局自动化对局，把胜率、击杀数、付费曲线等指标全部断言在区间内。你现在做的这套 GUT 仿真测试就是**最小可行版本的平衡测试机器人**。

把 Task 26、27、28 跑通后，你会得到一个**自带"防数值崩坏"护栏**的代码库——以后每次改任何数值（比如把伤害基数从 1 改成 2），CI 会立刻告诉你"30 秒平衡测试失败：玩家在 18 秒就死了"或"60 秒升级到了 25 级，节奏太快"。

这才是端到端 TDD 在游戏开发里的真正价值：**不只是"代码不崩"，更是"游戏好玩"也被测试守护着**。
