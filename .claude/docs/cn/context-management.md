# 上下文管理

上下文是 Claude Code 会话中最关键的资源。积极管理它。

## 文件支持的状态（主要策略）

**文件就是记忆，而不是对话。** 对话是临时的，会被
压缩或丢失。磁盘上的文件在压缩和会话崩溃后仍然存在。

### 会话状态文件

将 `production/session-state/active.md` 维护为实时检查点。在每个重要里程碑后更新它：

- 设计部分已批准并写入文件
- 架构决策已做出
- 实现里程碑已达到
- 测试结果已获得

状态文件应包含：当前任务、进度检查清单、已做出的关键决策、
正在处理的文件和未解决的问题。

### 状态行块（仅限 Production+）

当项目处于 Production、Polish 或 Release 阶段时，在 `active.md` 中包含一个结构化状态块，
状态行脚本可以解析：

```markdown
<!-- STATUS -->
Epic: 战斗系统
Feature: 近战战斗
Task: 实现命中框检测
<!-- /STATUS -->
```

- 所有三个字段（Epic、Feature、Task）都是可选的 —— 只包含适用的内容
- 切换焦点区域时更新此块
- 状态行将其显示为面包屑：`战斗系统 > 近战战斗 > 命中框`
- 当没有活动工作焦点时，删除或清空该块

在任何中断（压缩、崩溃、`/clear`）后，首先读取状态文件。

### 增量文件写入

在创建多部分文档（设计文档、架构文档、传说条目）时：

1. 立即创建带有骨架的文件（所有章节标题，空正文）
2. 在对话中一次讨论和起草一个部分
3. 每个部分一批准就写入文件
4. 每个部分后更新会话状态文件
5. 写入一个部分后，关于该部分的先前讨论可以安全地
   被压缩 —— 决策已经在文件中

这使上下文窗口只保存*当前*部分的讨论
（约 3-5k 令牌），而不是整个文档的对话历史（约 30-50k 令牌）。

## 主动压缩

- **主动压缩** 在约 60-70% 的上下文使用量时，而不是在限制时被动反应
- **使用 `/clear`** 在不相关的任务之间，或在 2+ 次失败的纠正尝试后
- **自然压缩点：** 写入部分到文件后、提交后、
  完成任务后、开始新主题前
- **聚焦压缩：** `/compact 专注于 [当前任务] —— 第 1-3 部分已写入文件，正在处理第 4 部分`

## 按任务类型的上下文预算

- 轻量（阅读/审查）：约 3k 令牌启动
- 中等（实现功能）：约 8k 令牌
- 繁重（多系统重构）：约 15k 令牌

## 子智能体委派

使用子智能体进行研究和探索，以保持主会话干净。
子智能体在自己的上下文窗口中运行，只返回摘要：

- **使用子智能体** 在跨多个文件调查、探索不熟悉的代码、
  或进行会消耗 >5k 令牌文件读取的研究时
- **使用直接读取** 当你确切知道要检查哪 1-2 个文件时
- 子智能体不继承对话历史 —— 在提示中提供完整上下文

## 压缩说明

当上下文被压缩时，在摘要中保留以下内容：

- 引用 `production/session-state/active.md`（读取它以恢复状态）
- 本次会话修改的文件列表及其用途
- 已做出的任何架构决策及其原理
- 活动冲刺任务及其当前状态
- 智能体调用及其结果（成功/失败/阻塞）
- 测试结果（通过/失败计数、具体失败）
- 未解决的阻塞或等待用户输入的问题
- 当前任务以及我们处于哪一步
- 当前文档的哪些部分已写入文件 vs 仍在进行中

**压缩后：** 读取 `production/session-state/active.md` 和任何正在
积极处理的文件以恢复完整上下文。文件包含决策；
对话历史是次要的。

## 会话崩溃后的恢复

如果会话崩溃（"提示太长"）或你开始新会话继续工作：

1. `session-start.sh` 钩子会自动检测并预览 `active.md`
2. 读取完整状态文件以获取上下文
3. 读取状态中列出的部分完成的文件
4. 从下一个未完成的部分或任务继续
